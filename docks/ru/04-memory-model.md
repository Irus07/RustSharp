## 1. Философия: почему гибридная модель?

В современных языках программирования существуют две крайности:

1. **Строгие системные языки (Rust, C++):**
   - Максимальная скорость, отсутствие сборщика мусора (GC), детерминированное освобождение памяти.
   - *Цена:* разработчик вынужден постоянно доказывать корректность времени жизни ссылок компилятору (борьба с Borrow Checker), что замедляет разработку бизнес-логики и усложняет циклические структуры данных (графы, деревья с обратными ссылками, UI-компоненты).

2. **Управляемые языки (C#, Go, Java):**
   - Высокая скорость разработки, автоматический сборщик мусора, простота работы со ссылками.
   - *Цена:* непредсказуемые паузы сборщика мусора (GC pauses), накладные расходы на заголовки объектов, память и барьеры записи (write barriers).

**RustSharp решает эту проблему через гибридный (адаптивный) подход:**
- По умолчанию компилятор пытается доказать время жизни объектов статически, как в Rust.
- Если статический анализ доказывает границы времени жизни — память освобождается **детерминированно и мгновенно (Zero-Cost RAII)** без участия GC.
- Если граф ссылок сложен (например, циклы или ссылки, покидающие область анализа) — компилятор **не выдаёт ошибку сборки**, а автоматически передаёт объект под контроль лёгкого рантайма (**Runtime Fallback**).
- Разработчик сохраняет контроль: ключевые слова `native` и `runtime` позволяют принудительно зафиксировать желаемый режим работы.

## 2. Архитектура сегментов памяти

В RustSharp память физически разделена на три сегмента:

```
+-----------------------------------------------------------------+
|                       ПАМЯТЬ RUSTSHARP                          |
+-------------------+--------------------+------------------------+
|    1. СТЕК        |  2. NATIVE HEAP    |   3. MANAGED HEAP      |
|    (Stack)        |    (RAII / LLVM)   |      (Runtime GC)      |
+-------------------+--------------------+------------------------+
| - Локальные прими- | - native struct /  | - class (сложные графы)|
|   тивы (int, bool)|   буферы           | - Циклические ссылки   |
| - Значения struct | - Статическое      | - Fallback-объекты     |
| - Ссылки и фреймы |   детерминированное| - Трассируемый сборщик |
|   вызовов         |   владение (own)   |   мусора (Tracing GC)  |
| - Мгновенный push/| - Без GC-пауз      | - Полная эргономика    |
|   pop при выходе  | - free в деструкторе|   ссылок               |
+-------------------+--------------------+------------------------+
```

### 2.1 Стек (Stack)
- Выделение происходит за одну инструкцию смещения указателя стека (`RSP`).
- Хранит примитивные типы (`int`, `i64`, `float`, `bool`), структуры `struct`, а также ссылки `&T`.
- Освобождается автоматически при выходе из области видимости фрейма функции.

### 2.2 Нативная куча (Native Heap / RAII)
- Память для динамических данных, чьё время жизни **доказано статически**.
- Управление строится на базе **семантики перемещения (Move Semantics)** и деструкторов.
- Компилятор LLVM генерирует прямой вызов аллокатора при создании и деаллокатора при выходе владельца из области видимости.
- Сборщик мусора **не сканирует** эту область памяти.

### 2.3 Управляемая куча (Managed Heap / GC)
- Память для объектов ссылочных типов (`class`) и данных, чьё время жизни невозможно однозначно ограничить статическим скоупом.
- Управляется встроенным рантаймом RustSharp (компактный Tracing/Generational GC).
- Объекты содержат служебный заголовок (тип, метаданные синхронизации, битмарка GC).

## 3. Концепция ключевых слов функций: `native`, `runtime` и нестрогий `fn`

RustSharp предлагает трёхуровневую градацию функций:

```rustsharp
// 1. Адаптивная (нестрогая) функция: компилятор решает сам
fn calculate_or_fetch(id: int) -> Data { ... }

// 2. Строго нативная функция: гарантия Zero-Cost, запрет GC
native fn matrix_multiply(a: &Matrix, b: &Matrix) -> Matrix { ... }

// 3. Строго управляемая функция: полный доступ к рантайму
runtime fn process_web_request(req: HttpRequest) -> HttpResponse { ... }
```

---

### 3.1 Гибридный режим по умолчанию (`fn`)

Обычное объявление `fn` — это **нестрогий (адаптивный)** контракт. Он спроектирован для максимального удобства прикладного разработчика:

```rustsharp
fn process_order(order_id: int) -> str {
    // 1. Компилятор видит локальную структуру на стеке
    var details: OrderDetails = OrderDetails(order_id);
    
    // 2. Если объект не «убегает» наружу, он очищается как native RAII
    var summary = details.Format();

    // 3. Если создается сложная циклическая связь (например, кэш подписчиков),
    //    компилятор не выдает ошибку borrow checker, а просто переводит
    //    эти связи в управляемую кучу (GC Fallback)
    EventBus.Subscribe(details); 

    return summary;
}
```

**Поведение компилятора в `fn`:**
- Запускается статический анализатор времени жизни.
- Если объект локален и время его жизни прозрачно — генерируется код нативной кучи/стека без сборщика мусора.
- Если обнаружено неоднозначное разделение владения или циклическая ссылка — компилятор тихо и прозрачно включает GC для этого фрагмента данных.
- Никаких ошибок *"cannot borrow as mutable more than once"* для кода, который можно разрешить через рантайм!

---

### 3.2 Строгий нативный режим (`native fn`)

Ключевое слово `native` перед `fn` вводит **строгий системный контракт (Zero-Cost Contract)**:

```rustsharp
native fn fast_fourier_transform(buffer: &var float[], size: int) -> void {
    // Гарантированно нулевые накладные расходы
    for i in 0..size {
        buffer[i] = buffer[i] * 0.5f;
    }
}
```

**Правила `native fn`:**
1. **Запрет GC-аллокаций:** внутри `native fn` запрещено неявное выделение памяти в Managed Heap.
2. **Строгий Borrow Checker:** если время жизни объекта не удаётся доказать статически, компилятор **генерирует ошибку сборки**, требуя от разработчика исправить владение или время жизни.
3. **C-ABI совместимость:** функция может быть напрямую скомпилирована в чистый экспортируемый символ LLVM для линковки с C/C++ библиотеками.
4. **Отсутствие точек останова GC (No Safepoints):** внутри функции не вставляются поллинги сборщика мусора, что критично для Realtime-систем, аудиопроцессинга и драйверов.

---

### 3.3 Управляемый режим (`runtime fn`)

Ключевое слово `runtime` перед `fn` явно декларирует, что функция выполняется в контексте среды исполнения:

```rustsharp
runtime fn build_ui_tree(root: Window) -> ComponentTree {
    var tree = ComponentTree();
    tree.AddChild(Button("Click me"));
    tree.AddChild(Label("Hello RustSharp"));
    return tree;
}
```

**Правила `runtime fn`:**
1. **Эргономика без компромиссов:** компилятор пропускает ресурсоёмкие этапы агрессивного доказательства времен жизни для классов. Все ссылочные объекты создаются в Managed Heap.
2. **Поддержка развитых рантайм-фич:** доступны рефлексия, динамический полиморфизм, события, сборка мусора с трассировкой ссылок.
3. **Регистрация корней GC:** локальные переменные функции автоматически учитываются сборщиком мусора при составлении карты корней (Stack Root Map).

---

### 3.4 Локальные блоки: `native { ... }` и `runtime { ... }`

Для точечного контроля внутри тела функций поддерживаются scoped-блоки:

```rustsharp
fn hybrid_worker() -> void {
    // Обычная логика
    var name = "Worker";

    native {
        // В этом блоке компилятор гарантирует zero-cost.
        // Любая попытка неявной аллокации в Managed Heap приведет к ошибке компиляции.
        var raw_buffer: byte[] = stackalloc byte[1024];
        raw_buffer[0] = 0xAA;
    }

    runtime {
        // В этом блоке явно разрешена работа с рантаймом даже внутри жестких ограничений
        GC.Collect();
    }
}
```

## 4. Владение (Ownership) и ссылки

RustSharp наследует фундамент концепции владения Rust, делая её опционально-строгой:

### 4.1 Перемещение владения (`own`)
Переменная-владелец единолично отвечает за ресурс. При передаче с ключевым словом `own` владение перемещается, а старая переменная инвалидируется:

```rustsharp
native fn process_packet(own packet: Packet) -> void {
    // packet уничтожится в конце функции детерминированно
}

var p = Packet();
process_packet(own p);
// p больше недоступен — компилятор выдаст ошибку при обращении к p
```

### 4.2 Заимствование и ссылки (`&`)
Для доступа без передачи владения используются ссылки:
- `&T` — неизменяемое заимствование (чтение).
- `&var T` — изменяемое заимствование (модификация).

```rustsharp
fn compute_length(s: &str) -> int {
    return s.Length;
}

fn increment(val: &var int) -> void {
    *val = *val + 1;
}
```

## 5. Алгоритм компилятора: Runtime Fallback

Как компилятор RustSharp принимает решение об аллокации в гибридной функции `fn`:

```
               [ Создание объекта / ссылки ]
                             |
                             v
               +---------------------------+
               | Контекст: `native fn`?    |
               +---------------------------+
                  /                     \
            Да   /                       \  Нет (обычный `fn`)
                v                         v
   [ Строгий Borrow Checker ]    [ Анализ побега (Escape Analysis) ]
        |             |                   |                 |
     Сходится      Ошибка            Побег доказан    Сложный граф/
        |         компиляции          детерминирован   неопределенность
        v                                 |                 |
  [ Native RAII ]                         v                 v
                                    [ Native RAII ]   [ Runtime GC Fallback ]
                                                      (Автоматически)
```

1. **Escape Analysis:** компилятор проверяет, покидает ли ссылка текущий стек или объемлющую структуру.
2. **Graph Complexity Check:** проверяется наличие циклов и множественных разделяемых связей.
3. **Fallback Decision:**
   - Если граф ацикличен и детерминирован $\rightarrow$ объект помещается на стек или в **Native Heap** (освобождение через деструктор).
   - Если есть неоднозначность или циклические ссылки $\rightarrow$ объект прозрачно переносится в **Managed Heap** (управление через GC).

## 6. Взаимодействие между мирами (Interop & Boundaries)

| Направление вызова | Механизм | Накладные расходы | Описание |
| :--- | :--- | :--- | :--- |
| **`runtime` $\rightarrow$ `native`** | Прямой вызов (Direct Call) | **0 (Zero-cost)** | Нативный код вызывается напрямую как C/LLVM функция. |
| **`native` $\rightarrow$ `runtime`** | Вход через рантайм-шлюз | Минимальные | Требует наличия активного контекста рантайма и регистрации фрейма. |
| **Передача структуры** | По значению или `&struct` | **0** | Структуры одинаково представлены в памяти обоих миров. |
| **Передача класса в native** | `pin` (закрепление ссылки) | Низкие | Объект закрепляется в памяти, чтобы GC не перемещал его во время работы `native`. |

### Пример закрепления (Pinning):
```rustsharp
runtime fn send_to_driver(device: Driver, data: ManagedBuffer) -> void {
    // pin фиксирует указатель в куче GC на время выполнения нативного блока
    pin (var ptr = &data[0]) {
        device.WriteNative(ptr, data.Length);
    }
}
```

## 7. Сводная таблица режимов функций

| Критерий | `native fn` | Обычный `fn` (Default) | `runtime fn` |
| :--- | :--- | :--- | :--- |
| **Философия** | Строгий zero-cost, системный код | Нестрогий, адаптивный, эргономичный | Высокоуровневый, управляемый |
| **Управление памятью** | Стек + Native Heap (RAII) | Гибридное (RAII $\rightarrow$ GC Fallback) | Managed Heap (GC) |
| **Ошибки Borrow Checker** | Всегда ошибка компиляции | Нет: fallback в GC при сложности | Не применяются к классам |
| **Сборщик мусора (GC)** | Полностью выключен | Подключается точечно по нужде | Активен |
| **Применение** | Hot-paths, FFI, математика, ядра | 80% прикладного кода, бизнес-логика | UI, плагины, скриптинг, графы |
